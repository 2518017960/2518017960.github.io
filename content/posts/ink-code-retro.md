这个站点从一句"我想照着某个博客的样子做一个自己的"开始，到最后能写字，前后大概花了不到一天。

这篇不是教程，是复盘。记录我**做对了什么、做错了什么，以及刻意不做什么**。

## 一、起点：先抄视觉，再想结构

动手前我做的第一件事不是选技术栈，而是把参考站点的 HTML 和 CSS 下载下来，看它的**设计令牌**：

```css
:root {
  --primary: 200 29% 45%;
  --background: 210 33% 99%;
  --muted: 240 4.8% 96%;
}
.dark {
  --primary: 195 95% 85%;
  --background: 240 20.54% 5.2%;
}
```

十几行变量，整个网站的调性就定了。这比截图比对着调色块高效得多。

> 经验一：**抄设计先抄变量**。变量对了，组件怎么写都像。

## 二、取舍一：不用前端框架

参考站是 Astro 构建的。我考虑过照搬，最后放弃了，原因很实际：

- 装依赖要几分钟，Node 版本还可能不对
- 每次构建要跑一遍打包器，改一行 CSS 等三秒
- 三年后再打开这个项目，`npm install` 大概率已经跑不通了

我选的是 **Python + 一个 Markdown 库**。构建时间 0.4 秒，零前端依赖，三年后 `pip install markdown` 还能跑。

代价是：没有组件化、没有热更新、没有生态。但一个博客不需要这些。

## 三、取舍二：自己写构建脚本

用现成的 SSG（Hugo / Hexo / Astro）当然更快。我不用，是因为**我需要知道每一行 HTML 是怎么来的**。

自己写的好处：

- 想加分页？改十行。
- 想让标签页带上文章数？改一行。
- 想给搜索加权重排序？加二十行。

坏处：所有功能都得自己实现。所以我把范围压得很小：

| 功能 | 做不做 | 理由 |
| --- | --- | --- |
| 文章 / 分页 / 标签 / 归档 | 做 | 内容组织的骨架 |
| 客户端搜索 | 做 | 没有它，写多了就找不到东西 |
| RSS | 做 | 十行代码，性价比极高 |
| 评论 | 不做 | 需要后端或第三方，还要处理垃圾评论 |
| 访问统计 | 不做 | 我不需要知道谁在看 |
| 博客后台 | 不做 | 编辑器就是后台 |

## 四、取舍三：视觉上"少做一点"

有三个地方我一度想加，最后删了：

1. **首页大图。** 加了之后第一屏看不见字，只剩一张图。"第一屏必须能看见字"是这次立的规矩。
2. **卡片入场动画。** 保留了一个极轻的 `fade-up`，但去掉了位移和缩放。滚动时反复触发动画会让人烦躁。
3. **鼠标跟随光标特效。** 很酷，但它会让人觉得这个站点"想被夸奖"。

> 经验二：**克制不是少做功能，是敢于删掉已经写好的功能。**

## 五、踩过的坑

**坑一：相对路径。** 第一次构建出来，首页正常，文章页全部白屏。因为文章页在 `blog/xxx/` 下，`assets/css/main.css` 解析成了 `blog/xxx/assets/...`。后来统一用「按深度算 `../` 前缀」解决。

**坑二：中文锚点。** 默认的 slugify 会把中文全部丢掉，导致所有中文标题的 `id` 都是空串，目录全指向同一个位置。换成 `slugify_unicode` 才对。

**坑三：深色模式闪白。** 主题脚本放在了 `</body>` 前，导致每次刷新都白闪一下。挪到 `<head>` 里同步执行就好了。

## 六、如果重来一次

我会做两件不同的事：

1. **先写三篇文章，再做站点。** 有了真实内容，才知道需要哪些功能。我一开始为"未来的大量文章"设计了分页，结果当时只有一篇。
2. **先定字号和行高，再定配色。** 阅读体验里，行高比主色重要十倍，但它最容易被忽略。

## 七、现在的结果

- 8 篇文章，18 个页面，600 KB
- 构建 0.4 秒
- 三层结构：`content/`（写作） → `build.py`（生成） → `dist/`（产物）
- 所有内容都是纯文本，Git 可追溯

下一步想做的：图片自动压缩、增量构建、以及给每篇文章加一个"最后修改时间"的自动读取。

但更重要的是——**赶紧去写第九篇**。工具已经够好了。
