「加了索引还是慢」是 SQL 优化里出现频率最高的一句话。拆开看，它其实是四个不同的问题。

## 一、B+ 树到底解决了什么

磁盘读一次是毫秒级，内存读一次是纳秒级。所以数据库优化的核心目标永远是：**减少随机 I/O 次数**。

B+ 树的关键设计有三条：

- 只有叶子节点存数据，非叶子节点只存键 → 同样大小的页能放下更多键 → 树更矮
- 叶子节点之间用链表相连 → 范围查询不用回到根节点
- 所有数据都在同一层 → 任何查询的 I/O 次数都是确定的

一个 3 层的 B+ 树，能存下大约 `1170 × 1170 × 16 ≈ 2000 万` 行。也就是说：**两千万行的表，点查只需要 3 次磁盘 I/O**。

这就是为什么"索引让查询变快"——它把 O(n) 的全表扫描变成了 O(log n) 的树查找。

## 二、最左前缀原则

联合索引 `(a, b, c)` 相当于按 `a`、再按 `b`、再按 `c` 排序。所以它能加速的查询有明确边界：

```sql
-- 能用上索引
WHERE a = 1
WHERE a = 1 AND b = 2
WHERE a = 1 AND b = 2 AND c = 3
WHERE a = 1 AND b > 2          -- a 精确, b 范围

-- 用不上（a 缺席）
WHERE b = 2
WHERE c = 3

-- 部分用上：a 精确匹配后 c 无法再用于排序
WHERE a = 1 AND c = 3
```

记住一句话：**范围条件会截断后续列**。`a > 1 AND b = 2` 里，`b` 只能做过滤（filter），不能做定位（seek）。

## 三、回表：真正的性能杀手

假设有 100 万行，查询 `SELECT * FROM t WHERE age = 20`，命中 10 万行。

即使 `age` 上有索引，数据库仍需要：
1. 在索引里找到 10 万个主键 → 10 万次索引查找
2. 用每个主键回聚簇索引取整行 → 10 万次随机 I/O

这时候全表扫描反而更快，因为顺序读比随机读便宜得多。**优化器知道这一点，所以它可能主动放弃索引**——这不是 bug。

解法是**覆盖索引**：把查询需要的列都放进索引里，让它不用回表。

```sql
-- 需要 age 和 name
ALTER TABLE users ADD INDEX idx_age_name (age, name);

SELECT name FROM users WHERE age = 20;  -- Using index，不回表
```

执行计划里出现 `Using index` 就说明成功了。

## 四、为什么索引用不上

排查顺序（按出现频率排）：

| 现象 | 原因 | 对策 |
| --- | --- | --- |
| 列上套了函数 | `WHERE DATE(created) = '2026-08-01'` | 改成范围：`>= '2026-08-01' AND < '2026-08-02'` |
| 隐式类型转换 | 字符串列传了数字 | 保持类型一致 |
| 前导模糊 | `LIKE '%abc'` | 改后缀匹配，或上全文索引 |
| 区分度太低 | 性别、状态这类只有几个值的列 | 建联合索引，把它放后面 |
| 统计信息过期 | 大批量写入后没 `ANALYZE` | `ANALYZE TABLE t` |

## 五、怎么读执行计划

```sql
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 42 AND status = 'paid';
```

只看三个字段就够入门：

- **type**：`const` > `eq_ref` > `ref` > `range` > `index` > `ALL`。看到 `ALL` 就该警觉。
- **rows**：预估扫描行数。预估与实际差一个数量级，说明统计信息有问题。
- **Extra**：`Using filesort` 和 `Using temporary` 是两个高频红灯。

## 六、我现在的检查清单

1. 这条 SQL 期望返回多少行？实际扫了多少行？
2. 有没有 `Using filesort`？排序字段在索引里吗？
3. 索引的**区分度**是多少？`COUNT(DISTINCT col) / COUNT(*)` 低于 0.1 基本没意义。
4. 是不是回表太多？能不能做成覆盖索引？
5. 最后才考虑：加机器、加缓存、分库分表。

> 大部分"慢查询"不是索引不够，是**索引不合适**。加索引是最容易的动作，也是最容易掩盖问题的动作。
